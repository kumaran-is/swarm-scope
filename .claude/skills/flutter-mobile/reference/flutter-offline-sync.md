# Flutter Offline Sync Patterns

Patterns for building offline-first Flutter apps: local queue, exponential backoff retry, conflict resolution, and connectivity-triggered sync.

Use these patterns when users must be able to create, edit, or delete data without an internet connection.

**Backend agnostic** — the queue logic, retry math, and sync manager are pure Dart. Only the local persistence layer (Hive by default) and the remote data source (your own interface) are implementation choices.

---

## How it works

```
User creates entry (offline)
        │
        ▼
Save to local DB immediately        ← user never waits
        │
        ▼
Add to SyncQueue (Hive box)         ← queued for upload
        │
        ▼
Connectivity comes back
        │
        ▼
SyncManager picks up queue          ← runs on timer + connectivity event
        │
   ┌────┴────┐
success    failure
   │           │
Remove      recordFailure()
from         │
queue       wait backoff (1→2→4→8→16→32→60 min)
            │
           retry until maxAttempts (10)
```

## 1. Domain Layer — `SyncOperation` enum

Pure domain enum. No framework dependencies. Add operations relevant to your domain.

```dart
// lib/core/domain/entities/sync_operation.dart
enum SyncOperation {
  create,
  update,
  delete;

  /// Delete operations are highest priority — process before creates/updates
  bool get isDelete => this == SyncOperation.delete;

  /// Delete requires the remote ID to identify which remote record to remove
  bool get requiresRemoteId => this == delete;
}
```

## 2. Data Layer — `SyncQueueItem` (Hive model)

Stores one pending operation on-device. The `payload` is `Map<String, dynamic>` — backend-agnostic. Swap Hive for Isar or SQLite by replacing the annotations and generated file only; the logic stays identical.

```dart
// lib/core/data/local/models/sync_queue_item.dart
import 'package:hive_ce/hive.dart';
import '../../../domain/entities/sync_operation.dart';

part 'sync_queue_item.g.dart'; // generated by build_runner

@HiveType(typeId: 11)
class SyncQueueItem extends HiveObject {
  @HiveField(0) final String id;
  @HiveField(1) final String localId;
  @HiveField(2) final SyncOperation operation;
  @HiveField(3) final Map<String, dynamic> payload; // backend-agnostic
  @HiveField(4) int attempts;
  @HiveField(5) DateTime nextRetryAt;
  @HiveField(6) final DateTime createdAt;
  @HiveField(7) String? lastError;

  SyncQueueItem({
    required this.id,
    required this.localId,
    required this.operation,
    required this.payload,
    this.attempts = 0,
    required this.nextRetryAt,
    required this.createdAt,
    this.lastError,
  });

  factory SyncQueueItem.immediate({
    required String localId,
    required SyncOperation operation,
    required Map<String, dynamic> payload,
  }) {
    final now = DateTime.now();
    return SyncQueueItem(
      id: 'sync_${now.millisecondsSinceEpoch}',
      localId: localId,
      operation: operation,
      payload: payload,
      nextRetryAt: now, // immediate first attempt
      createdAt: now,
    );
  }

  // Exponential backoff: 1m → 2m → 4m → 8m → 16m → 32m → 60m (max)
  void recordFailure(String error) {
    attempts++;
    lastError = error;
    final backoffMinutes = switch (attempts) {
      1 => 1,  2 => 2,  3 => 4,
      4 => 8,  5 => 16, 6 => 32,
      _ => 60,
    };
    nextRetryAt = DateTime.now().add(Duration(minutes: backoffMinutes));
  }

  void recordSuccess() {
    lastError = null;
    // Set far-future date so cleanup query finds completed items easily
    nextRetryAt = DateTime.now().add(const Duration(days: 365));
  }

  bool get isReadyForRetry   => DateTime.now().isAfter(nextRetryAt);
  bool get hasExceededMaxRetries => attempts >= 10;
  bool get isPending         => attempts == 0;

  /// Delete > Create > Update — ensures deletes don't leave orphaned creates
  int get priority => operation.isDelete ? 0 : 1;
}
```

## 3. Service Layer — `SyncManager`

Coordinates queue, connectivity, and the remote data source. The `RemoteDataSource` type parameter is your own abstract interface — swap it for Firebase, Supabase, REST, or anything else.

```dart
// lib/core/data/sync/sync_manager.dart
import 'dart:async';
import 'package:hive_ce/hive.dart';
import 'package:riverpod_annotation/riverpod_annotation.dart';

part 'sync_manager.g.dart';

abstract class RemoteDataSource<T> {
  Future<T> create(T item);
  Future<T> update(T item);
  Future<void> delete(String remoteId);
}

class SyncManager<T> {
  SyncManager({
    required this.localDataSource,
    required this.remoteDataSource,
    required this.toPayload,
    required this.fromPayload,
  });

  final Future<T?> Function(String localId) localDataSource;
  final RemoteDataSource<T> remoteDataSource;
  final Map<String, dynamic> Function(T item) toPayload;
  final T Function(Map<String, dynamic> payload) fromPayload;

  static const _queueBoxName = 'sync_queue';
  static const _syncInterval = Duration(minutes: 15);

  Box<SyncQueueItem>? _box;
  Timer? _timer;
  StreamSubscription<bool>? _connectivitySub;
  bool _syncing = false;
  bool _online = true;

  final _statusController = StreamController<SyncStatus>.broadcast();
  Stream<SyncStatus> get status => _statusController.stream;

  Future<void> initialize(Box<SyncQueueItem> box, Stream<bool> connectivity) async {
    _box = box;

    // Sync immediately when connectivity is restored
    _connectivitySub = connectivity.listen((online) {
      _online = online;
      if (online) unawaited(sync());
    });

    // Periodic sync as safety net (catches items missed by connectivity events)
    _timer = Timer.periodic(_syncInterval, (_) => sync());
  }

  /// Enqueue an operation. Call this immediately after saving to local DB.
  Future<void> enqueue(
    SyncOperation operation,
    String localId,
    Map<String, dynamic> payload,
  ) async {
    final item = SyncQueueItem.immediate(
      localId: localId,
      operation: operation,
      payload: payload,
    );
    await _box!.put(item.id, item);
    if (_online) unawaited(sync()); // try immediately if online
  }

  /// Process all ready queue items.
  Future<void> sync() async {
    if (_syncing || !_online) return;
    _syncing = true;
    _statusController.add(SyncStatus.syncing);

    try {
      final ready = _box!.values
          .where((i) => i.isReadyForRetry && !i.hasExceededMaxRetries && !i.isCompleted)
          .toList()
        ..sort((a, b) => a.priority.compareTo(b.priority));

      for (final item in ready) {
        try {
          await _processItem(item);
          item.recordSuccess();
        } catch (e) {
          item.recordFailure(e.toString());
        }
        await _box!.put(item.id, item);
      }

      // Remove permanently completed items
      final completed = _box!.values
          .where((i) => i.nextRetryAt.isAfter(DateTime.now().add(const Duration(days: 300))))
          .map((i) => i.id)
          .toList();
      await _box!.deleteAll(completed);

      _statusController.add(SyncStatus.synced);
    } finally {
      _syncing = false;
    }
  }

  Future<void> _processItem(SyncQueueItem item) async {
    final local = await localDataSource(item.localId);
    if (local == null) return; // deleted locally before sync ran — skip

    switch (item.operation) {
      case SyncOperation.create:
        await remoteDataSource.create(local);
      case SyncOperation.update:
        await remoteDataSource.update(local);
      case SyncOperation.delete:
        final remoteId = item.payload['remoteId'] as String?;
        if (remoteId != null) await remoteDataSource.delete(remoteId);
    }
  }

  void dispose() {
    _timer?.cancel();
    _connectivitySub?.cancel();
    _statusController.close();
  }
}

enum SyncStatus { idle, syncing, synced, failed }
```

## 4. Riverpod Integration

```dart
// lib/core/providers/sync_providers.dart
@Riverpod(keepAlive: true)
SyncManager<JournalEntry> syncManager(Ref ref) {
  final manager = SyncManager<JournalEntry>(
    localDataSource: (id) => ref.read(localEntryRepoProvider).getById(id),
    remoteDataSource: ref.read(remoteEntryDataSourceProvider),
    toPayload: (e) => e.toJson(),
    fromPayload: JournalEntry.fromJson,
  );

  // Wire up connectivity stream
  final connectivity = ref.read(connectivityServiceProvider);
  final box = ref.read(syncQueueBoxProvider);
  manager.initialize(box, connectivity.onConnectivityChanged);

  ref.onDispose(manager.dispose);
  return manager;
}

// Show sync status in UI
@riverpod
Stream<SyncStatus> syncStatus(Ref ref) {
  return ref.watch(syncManagerProvider).status;
}
```

## 5. Usage — enqueue after every local write

  // 2. Enqueue for background upload — fire and forget
  await ref.read(syncManagerProvider).enqueue(
    SyncOperation.create,
    saved.localId,

  );

  return Success(saved);

## Swapping the Local Storage Layer

The only Hive-specific parts are:
- `@HiveType(typeId: N)` and `@HiveField(N)` annotations on `SyncQueueItem`
- `part 'sync_queue_item.g.dart'`
- `Box<SyncQueueItem>` in `SyncManager`

To use **Isar** instead: remove Hive annotations, add `@collection` + `@Id`, replace `Box<T>` with `IsarCollection<T>`.
To use **SQLite (drift)**: define a table row class and replace `Box<T>` with a drift DAO.

Everything else — the backoff math, the priority sort, the retry loop, the `RemoteDataSource<T>` interface — stays identical.

---

## Rules

- **Always save locally first, then enqueue** — never wait for the remote call before showing the user success
- **`enqueue()` is fire-and-forget from the UI layer** — the repository handles it; widgets never call `SyncManager` directly
- **`maxRetries: 10` with 60-min cap** — after 10 failures (~10 hours cumulative) the item is permanently failed; surface this to the user
- **Delete operations must be highest priority** — process before creates/updates to prevent orphaned remote records
- **One `SyncManager` instance** — `keepAlive: true` Riverpod provider; never recreate per feature
- **Do not enqueue the same `localId` + `operation` twice** — check for existing pending item before enqueuing to prevent duplicate uploads

## 7. Conflict Resolution

When the same record is modified both locally (offline) and on the server (by another device or user), the sync manager needs a strategy to resolve the conflict.

### Strategy selection

| Strategy | When to use | Tradeoff |
|----------|-------------|----------|
| **Server wins** | Server is authoritative (financial records, inventory) | Simple; local edit is silently lost |
| **Last write wins** | User-owned data (notes, preferences) | Simple; requires `updatedAt` timestamps on both sides |
| **Client wins** | Rare — only if local is always more current | Risk of overwriting legitimate server changes |
| **User prompt** | High-value data where silent loss is unacceptable (documents, schedules) | Best UX; requires UI to surface the conflict |

---

### Strategy 1 — Last Write Wins (timestamp comparison)

Attach a client-side `updatedAt` timestamp to every sync operation payload. The server rejects stale writes.

```dart
// Add to SyncQueueItem payload when enqueuing
Future<Result<T>> createEntry(JournalEntry entry) async {
  final saved = await _localRepo.create(entry);

  await ref.read(syncManagerProvider).enqueue(
    SyncOperation.update,
    saved.localId,
    {
      ...saved.toJson(),
      // ISO-8601 — server compares against its own updatedAt
      'client_updated_at': DateTime.now().toUtc().toIso8601String(),
    },
  );
  return Success(saved);
}
```

Server logic (pseudo-code — backend responsibility):
```
if request.client_updated_at > server_record.updated_at:
    apply update
    return 200
else:
    return 409 Conflict { "server_version": server_record }
```

Handle the 409 in `SyncManager._executeOperation()`:
```dart
// In the catch block of _executeOperation inside SyncManager
on ConflictException catch (e) {
  // Last-write-wins: server data is fresher — overwrite local
  await _localRepo.update(e.serverVersion);
  // Remove from queue — conflict resolved by accepting server state
  await _box.delete(item.localId);
}
```

### Strategy 2 — User Prompt (for high-value data)

Surface the conflict to the user when silent loss is unacceptable.

```dart
// lib/core/sync/conflict_resolver.dart

@freezed
class SyncConflict<T> with _$SyncConflict<T> {
  const factory SyncConflict({
    required String entityId,
    required T localVersion,
    required T serverVersion,
    required DateTime localUpdatedAt,
    required DateTime serverUpdatedAt,
  }) = _SyncConflict;
}

enum ConflictResolution { keepLocal, keepServer, keepBoth }
```

```dart
// Riverpod provider — emits conflicts for the UI to present
@riverpod
class ConflictQueue extends _$ConflictQueue {
  @override
  List<SyncConflict<Map<String, dynamic>>> build() => const [];

  void add(SyncConflict<Map<String, dynamic>> conflict) =>
      state = [...state, conflict];

  Future<void> resolve(
    String entityId,
    ConflictResolution resolution,
  ) async {
    final conflict = state.firstWhere((c) => c.entityId == entityId);
    switch (resolution) {
      case ConflictResolution.keepLocal:
        // Force-push local version with a newer timestamp
        await ref.read(syncManagerProvider).enqueue(
          SyncOperation.update,
          entityId,
          {...conflict.localVersion, 'force': true},
        );
      case ConflictResolution.keepServer:
        await ref.read(localRepoProvider).update(conflict.serverVersion);
      case ConflictResolution.keepBoth:
        // App-specific — e.g. duplicate the record with a suffix
        await ref.read(localRepoProvider).create(
          {...conflict.localVersion, 'localId': '${entityId}_local_copy'},
        );
        await ref.read(localRepoProvider).update(conflict.serverVersion);
    }
    state = state.where((c) => c.entityId != entityId).toList();
  }
}
```

```dart
// Widget — show conflict banner when queue is non-empty
@riverpod
Widget conflictBanner(WidgetRef ref) {
  final conflicts = ref.watch(conflictQueueProvider);
  if (conflicts.isEmpty) return const SizedBox.shrink();

    actions: [
      TextButton(

      ),
    ],
  );
}
```

### Integration with SyncManager

Add conflict detection in `_executeOperation()` inside `SyncManager`:

```dart
// In _executeOperation — catch the 409 from the remote source
try {
  switch (item.operation) {
    case SyncOperation.create: await _remote.create(item.payload); break;
    case SyncOperation.update: await _remote.update(item.localId, item.payload); break;
    case SyncOperation.delete: await _remote.delete(item.localId); break;
  }
  await _box.delete(item.localId);   // success — remove from queue
} on ConflictException catch (e) {
  // Route to the appropriate strategy:
  // Strategy 1 (last-write-wins):  accept server version, clear queue item
  // Strategy 2 (user prompt):      push to ConflictQueue provider
  _handleConflict(item, e.serverVersion);
}
```

---

### Rules

- **Choose one strategy per entity type** — mixing strategies in the same feature creates unpredictable behaviour
- **Always include `updatedAt` in sync payloads** — without it, last-write-wins is impossible to implement correctly
- **Never silently drop user edits for high-value data** (documents, schedules, financial entries) — use user prompt strategy
- **`keepBoth` is a last resort** — it creates data duplication; prefer last-write-wins or user prompt
- **Conflicts must be surfaced, not suppressed** — if using user prompt strategy, show a badge/banner count in the UI so users know action is needed
